# 플랫폼 노트

수집기와 OS 조합마다 노트 하나를 이 디렉터리에 둔다. 파일 이름은 `<수집기>-<os>.md`
(`wifi-windows.md`, `ble-macos.md`)다. 배포 대상은 Windows와 macOS이고, 리눅스는
devtools용 노트만 둔다. 수집기 코드는 이 노트에서 출발한다(`add-collector` 스킬).

가장 먼저 **송신 여부**를, 그다음 **라이선스**를 적는다. 연결·광고·주입이 필요한 API라면 그 수집기는 만들 수
없다(AGENTS.md §3.1–§3.2). 함께 링크되는 C 라이브러리의 라이선스는 리뷰가 확인한다(§3.7).

## 템플릿

```markdown
# <수집기> — <OS>

- 상태: 초안 | 구현됨 | 실측 확인됨
- 단계: Phase N
- API·크레이트·장비: 이름과 버전, 공식 문서 링크

## 송신 여부

이 API·장비가 무엇을 내보내는가. 능동 스캔이면 스캔 요청·probe request를 보낸다는 사실과 수동 스캔을 고를 수
있는지(Windows BLE는 수동). 장비 펌웨어에 송신 기능이 있다면 그 명령을 보내지 않는다는 것.

## 라이선스

크레이트와 함께 링크되는 C 라이브러리(libhackrf, SoapySDR 등)의 라이선스와 링크 방식(동적·정적).

## 얻는 필드

| API 필드 | `Observation` 필드 | 허용 목록(AGENTS.md §3.2) |
|---|---|---|
| | | 사용 / 받지만 버림 |

## 권한

필요한 권한(Windows 정밀 위치, macOS 위치·블루투스 권한, Developer ID 서명, 사용자 세션)과 장비
드라이버, 권한이 없을 때 보고할 상태와 권한 온보딩·점검 모드에서 보여 줄 안내.

## 제약

스캔 주기 제한, 지원 대역(2.4/5/6GHz), 칩·드라이버 의존성, OS 버전별 차이(macOS 14/15/26 등), 첫 관측 지연.

## 변환

원시 데이터 → `Observation` 순수 함수의 이름과, 사양대로 조립할 테스트 입력.

## 미검증

공식 문서로 확인하지 못한 동작, 실측이 필요한 것.
```
