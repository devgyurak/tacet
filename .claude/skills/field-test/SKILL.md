# 실측 계획과 기록

경계·신뢰도 기준과 기기 특성은 문서만으로 정할 수 없다(설계 §4.4, §10). 실측은 필요하지만, 실측이야말로 남의
기기 정보와 원본 캡처가 저장소에 들어오기 가장 쉬운 길이다. 그래서 절차를 지킨다.

## 원칙

- **실측은 사람이 한다.** 에이전트는 계획을 세우고, 결과 요약을 정리하고, 노트와 설정에 반영한다. 에이전트는 무선
  하드웨어를 직접 조작하지 않고 송신 도구를 실행하지 않는다(AGENTS.md §3.1).
- **우리 기기만.** 기준 폰·안경·핫스팟은 실측하는 사람이 소유하거나 빌린 기기다. 주변의 다른 사람 기기는 측정 대상이
  아니며 결과에 남기지 않는다.
- **흔적은 기기가 스스로 낸다.** 핫스팟 켜기, 안경 연동, "Hey Meta" 질문 같은 송신은 기기의 정상 기능으로 사람이 켠다.
  우리 도구는 수신만 한다.
- **원본은 남기지 않는다.** 캡처·Kismet DB·관측 녹화(`.obslog`)·스캔 원본은 측정한 컴퓨터에만 두고 기록 후 지운다.
  저장소에는 요약 수치만(AGENTS.md §3.3). MAC·SSID·기기 이름 대신 "폰 A(안드로이드, 핫스팟 6GHz)" 같은 라벨을 쓴다.
- **실제 시험장 적용은 별개다.** 실측은 빈 교실·실험 공간에서 한다. 실제 시험 중 사용은 주관 기관 승인과 법률 검토가
  필요하다(설계 §8).

## 1. 무엇을 확인할지 정한다

`TODO(field-unverified)`와 규칙·플랫폼 노트의 "미검증", 설계 §10의 실측 항목에서 고른다.

```bash
rg -n "TODO\(field-unverified\)" crates docs
```

항목마다 질문을 한 문장으로 쓴다: "폰 A를 교실 뒤쪽 앞주머니에 넣었을 때 BLE 광고를 10회 중 몇 번 잡고, 첫
관측까지 몇 초 걸리는가?"

자주 쓰는 계획:

- **교실 보정**(설계 §4.4) — 기준 폰을 교탁, 교실 뒤쪽, 복도, 옆 교실에 두고 각 센서의 RSSI 중앙값을 잰다. 결과는
  교실별 "교실 내부" 경계로 설정 파일에 넣는다. 기록에는 교실 이름 대신 라벨.
- **안경·폰 특성** — 안경 연동 뒤 광고 지속 여부(R1a), 사진 전송 중 `DIRECT-` 비콘(R6), 거리·차폐(앞주머니·뒷주머니·
  가방 × 1/3/6m).
- **위치 판정 신뢰도**(설계 §4.7) — 인접 교실 세 개에서 1·2위 RSSI 중앙값 차이와 실제 교실의 일치율.
- **플랫폼** — macOS 14/15/26의 CoreWLAN BSSID 수신, Windows 정밀 위치 권한 흐름, Windows BLE 수동 스캔.

## 2. 계획을 쓴다

`docs/field/<YYYY-MM-DD>-<영어-케밥>.md`를 템플릿(`docs/field/README.md`)으로 만들고 측정 전에 채운다: 질문, 장소
조건(교실 크기, 벽 재질, 층), 기기 라벨과 설정, 수집기·OS 버전·어댑터, 거리·위치 격자, 반복 횟수, 판정
기준(어떤 결과면 경계·신뢰도 기준을 어떻게 정할지).

## 3. 측정은 사람이, 요약은 함께

사람이 측정하고 우리 앱(또는 devtools)의 요약 출력(규칙별 적중, RSSI 중앙값, 탐지율, 첫 관측 시간)을 공유한다. 원본
출력에 주소·SSID가 섞여 있으면 붙여넣기 전에 지우게 안내한다. 에이전트는 받은 요약을 표로 정리한다.

## 4. 반영한다

- 기록에 결론과 한계(표본 수, 한 건물·한 기종)를 쓴다.
- 규칙·플랫폼 노트의 "미검증"을 갱신하고 기록을 링크한다.
- 기본 가중치·신뢰도 기준을 바꾸면 그것은 `add-rule` 절차와 `decision` 이슈의 일이다. 교실 보정값은 설정이고 코드
  상수가 아니다. 해소된 `TODO(field-unverified)`를 지운다.

## 5. 검토

기록과 노트는 `DOCS:` 변경이다. 그래도 `compliance-auditor`에게 기록에 식별 가능한 정보가 없는지 확인받는다.
