# 탐지 규칙 추가·변경

순서대로 한다. 곧장 코드로 가는 것이 이 절차가 막으려는 실패다: 노트 없는 규칙은 왜 그 조건인지 아무도
모르고, 실패한 적 없는 테스트는 규칙이 맞다는 것을 증명하지 못하며, 오탐 검토 없는 규칙은 시험장에서
수험생을 불필요하게 의심하게 만든다.

## 0. 이 단계의 일인가

`docs/STATUS.md`를 읽는다. 규칙이 이후 단계 소관이면(예: Phase 1에서 R7 SDR 규칙, Phase 2.5의 위치 판정) 현재 단계에 필요한
만큼만 하고 `TODO(phaseN)` 스텁을 남긴다. 어느 단계 소관인지 모르면 묻는다.

## 1. 위협과 흔적을 정한다

`docs/DESIGN.md` §3 위협 표에서 이 규칙이 막는 위협(T1–T7)과 그 위협이 남기는 흔적을 적는다. 막는 위협이
없는 규칙은 만들지 않는다. 블루투스조차 쓰지 않는 기기와, 광고 없이 블루투스 연결만 남기는 기기(설계 §3의 T6·T7)는 범위 밖이다(사용자 결정
2026-11-16). 같은 위협을 잡는 다른 규칙(예: 폰 광고는 R1, 촬영 전송은 R6)과의 관계를 적는다.

## 2. 규칙 노트를 쓴다

`docs/rules/<규칙ID>-<영어-케밥>.md`(위치 판정·보정은 `L-<영어-케밥>.md`), 템플릿은 `docs/rules/README.md`.

- **조건**은 코드로 옮길 수 있을 만큼 정확하게: 필드, 비교 연산자, 경계 포함 여부(`≥ 교실 보정 경계`). **고정 dBm
  임계치는 쓰지 않는다**(설계 §4.4) — 교실별 보정값과 기준선 대비 상대 변화로 쓴다.
- **근거 출처**: 제조사 ID·서비스 UUID는 Bluetooth SIG Assigned Numbers와 설계 §11, MAC 비트는 IEEE 802, 광고 구조는
  Bluetooth 코어 규격, 채널·대역은 IEEE 802.11과 3GPP 표. 기억으로 쓰지 않는다.
- **쓰는 필드가 AGENTS.md §3.2 허용 목록 안인지** 확인한다. 패킷 본문, 블루투스 연결 패킷, 셀룰러 식별자가 필요하다면
  그 규칙은 만들 수 없다 — 멈추고 사용자에게 알린다.
- **플랫폼 차이**: 어느 수집기·OS에서 흔적이 오는지, macOS `HostLocal` UUID처럼 센서 간 비교가 안 되는 값이 있는지.
- **오탐 요인**: 설계 §4.3·§4.7의 요인마다 이 규칙이 어떻게 반응하는지, 무엇이 걸러내는지(옆 교실 기기는 버리지
  않고 재배정한다).
- **미검증**: 실측하지 않은 보정 경계·신뢰도 기준·기기 특성·첫 관측 지연. 코드 위치에 `TODO(field-unverified)`가 붙을 곳과 확인
  방법(`field-test` 스킬)을 적는다.

## 3. 실패하는 테스트부터

`test-author`에 맡기거나 AGENTS.md §5를 직접 따른다.

- **양성 시나리오**: 노트의 위협(T#)을 합성 관측 열로 만들고 기대 적중·알림을 단언한다.
- **음성 시나리오**: 노트의 오탐 요인마다 알림이 없음(또는 옆 교실 배정)을 단언한다.
- **위치 판정**이면 센서 여러 대의 `SensorReport`로 기대 교실·앞뒤·신뢰도·근거를 단언한다.
- **경계**: 보정 경계와 같은 값, 보정값 없음, 기준선 창 끝, 랜덤 MAC 교체, 신뢰도 경계 등 노트에 적은 경계.
- 기대값은 노트에서 온다. 구현을 돌려 나온 값을 쓰지 않는다. 식별자는 합성 값만(AGENTS.md §3.3).

돌려서 **예상한 이유로 실패하는지** 본다.

## 4. core에 구현한다

`crates/core/`의 규칙 모듈에서. AGENTS.md §2와 맞춰 본다:

- `Rule::score(&Observation, &Baseline) -> Option<Hit>`는 순수하다. 시계·IO·난수 없음.
- 가중치와 점수는 정수다. 기본값은 설정에 두고 이름 있는 상수로 출처를 적는다. 절대 dBm 판정 상수는 두지 않는다.
- 중앙값은 정한 규칙(짝수 개면 아래쪽)으로, 신뢰도 기준은 설정으로.
- 상수(제조사 ID, UUID, 접두사)는 이름을 붙이고 문서 주석에 출처와 노트 경로를 쓴다.
- 미검증 항목마다 코드에 `TODO(field-unverified)`.
- 컬렉션은 `Vec`/`BTreeMap`, 동점은 (타임스탬프, 센서 ID, 수집 순번).
- 화이트리스트가 규칙 적중보다 앞선다.

## 5. 검토

`./scripts/verify.sh`(`verify` 스킬). 그다음 **한 메시지에서, 새 세션으로** `detection-reviewer`,
`architecture-guard`, `compliance-auditor`를 병렬로 부른다. 지적 사항을 고치고 다시 돌린다.

## 6. 결정을 남긴다

기본 가중치·신뢰도 기준, 점수·위치 판정 모델, 기기 상관 방식처럼 되돌리기 비싼 결정은 `.github/ISSUE_TEMPLATE/decision.md`로
`decision` 라벨 이슈에 남기고 PR이 링크한다. 이슈 초안은 사용자가 요청할 때만 쓰고, 결정은 사용자가 한다.

## PR

PR 하나 = 이 규칙 하나. 제목 `ADD: <규칙ID> <동작>`(변경이면 `FIX:` 또는 `REF:`). 본문에 규칙 노트, 막는
위협(T#), 고정하는 테스트, 오탐 검토 결과, 미검증 항목, 바뀐 스냅숏과 그 이유를 적는다.
