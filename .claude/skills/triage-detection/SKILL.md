# 오탐·미탐 조사

순서가 중요하다. 고정된 재현과 실패하는 테스트 없는 수정은 추측이고, 탐지기에서 추측은 다른 시험장의
오탐이나 미탐으로 돌아온다.

## 1. 재현을 익명화해서 고정한다

core는 결정적이므로 같은 관측 열이면 같은 결과가 나온다. 재현이 한 번 되면 늘 된다 — 안 된다면 **그것이**
버그다(결정성 누수, `verify` 스킬의 결정성 실패 참고).

- 사용자가 보고한 상황을 **합성 시나리오**로 옮긴다: 어떤 종류의 기기(폰 BLE, 안경 BLE, 숨긴 핫스팟, Wi-Fi Direct,
  옆 교실 기기), 센서별 대략적 RSSI, 나타난 시각, 기준선에 있었는지, 센서 OS(Windows 주소인지 macOS UUID인지).
- **실제 MAC, SSID, 기기 이름, 캡처·녹화를 대화나 저장소로 가져오지 않는다**(AGENTS.md §3.3).
  식별자는 합성 값으로 바꾸고 같은 기기인지 여부만 보존한다(`doc_mac(0x01)`, `doc_mac(0x2A)`). SSID는 "숨김",
  "DIRECT- 접두사", "일반" 같은 범주로만.
- 사용자가 관측 녹화(`.obslog`)나 캡처를 갖고 있으면 devtools로 재생해서 **점수·위치 분해 출력**만 받는다. 그 바이트는
  읽지 않는다.

## 2. 첫 갈림점을 찾는다

점수를 규칙별 적중으로, 위치를 센서별 RSSI 중앙값으로 분해한다: 어느 규칙이 맞았고(또는 안 맞았고) 가중치가
얼마였는지, 기준선 비교와 교실 보정 결과, 기기 상관이 무엇을 묶었는지(macOS UUID를 잘못 묶지 않았는지), 1·2위 교실과
신뢰도, 화이트리스트가 적용됐는지. 관측 → 수집기 변환 → 센서 보고서·시각 정렬 → 기기 상관 → 규칙 → 점수 → 위치 판정
→ 알림 순서로 따라가며 **처음으로 기대와 달라지는 곳**을 찾는다. 그 뒤의 차이는 결과일 뿐이니 "고치지" 않는다.

미탐이면 먼저 수집기 상태를 본다. 수집기가 꺼져 있었거나(위치·블루투스 권한, 드라이버 미바인딩, 대역 미지원) 관측
자체가 없었다면 규칙이 아니라 수집 공백이고, 그 공백이 감독관과 점검 모드에 보였는지가 문제다. 광고 간격이 긴 기기는 첫 관측
지연을 먼저 의심한다. 광고 없이 블루투스 연결만 남기는 기기는 범위 밖이다(설계 §3). 위치 오판이면 센서 시각(NTP) 어긋남, 보정값 누락, 인체 차폐를 먼저 본다.

## 3. 규칙 노트와 대조한다

갈림점의 규칙이나 플랫폼 노트를 연다. 없으면 먼저 쓴다(`add-rule` 1–2단계, `add-collector` 1단계).

- 노트와 기대가 맞고 코드가 다르다 → 우리 버그.
- 노트가 그 상황을 다루지 않는다 → 노트의 빈틈. 오탐 요인이나 경계에 더하고, 실측이 필요하면 미검증으로
  남긴다(`field-test`).
- 노트와 사용자의 기대가 다르다 → 멈추고 보고한다. 조용히 한쪽을 고르지 않는다. 임계치·가중치를 바꾸는
  것은 `add-rule` 절차와 `decision` 이슈의 일이다.

## 4. 실패하는 테스트, 그다음 수정

익명화한 재현을 지금 실패하는 테스트로 더한다(`test-author`): 오탐이면 "알림 없음"을, 미탐이면 기대 알림을,
위치 오판이면 기대 교실·신뢰도를 단언하는 시나리오. 이름은 동작으로 짓는다(`given_collected_phone_left_on_when_watched_then_no_alert_is_raised`).
그다음 고치고 통과를 본다. 같은 규칙의 기존 양성·음성·위치 시나리오가 모두 그대로인지 확인한다 — 오탐을 줄이다
미탐을 만들기 쉽고, 고정 임계치로 "고치면" 다른 교실에서 깨진다.

## 5. 검증과 보고

`./scripts/verify.sh`, 그다음 새 세션에서 `detection-reviewer`와 `architecture-guard`를 병렬로(수집기를
고쳤으면 `compliance-auditor`도). PR(`FIX: <동작>`)에 첫 갈림점, 어긴 규칙 노트 조항, 고정한 테스트, 다른
위협(T1–T7)에 미치는 영향, 바뀐 스냅숏과 이유를 적는다.
